# 0.1.0-alpha.10：可靠性与设置界面修复

本版保留已验证的宿主接入、三通道与原字节传输核心，集中修复状态一致性、异常路径和卡片层级。

## 为什么选择修复

以相同交付要求估算，修复约需重写的一半工作量。下表是相对工作量，不是已测得的工时；1 单位代表一个规模接近的实现与验证工作块。

| 工作范围 | 修复 | 重写 |
| --- | ---: | ---: |
| Harness 注册、兼容与配置基础 | 1 | 4 |
| Chat 协议、媒体原字节传输 | 2 | 5 |
| 媒体归属、恢复和保存竞态 | 3 | 4 |
| 输入入口、供应商与模型卡 | 2 | 3 |
| 回归、安装、发布与接手 | 3 | 5 |
| 合计 | **11** | **21** |

基线已有 271 项测试，问题集中在明确的边界。重写仍需要重新验证协议、Host ABI、原字节持久化和旧版本兼容。估算有约三成不确定性，但现有证据不足以支持推倒重来；未来若宿主公共接口发生破坏性变化，应重新计算。

## 修复内容

- 分两次选择媒体后恢复草稿，按宿主 detect 坐标插入 chip；保留全部原正文和其他插件引用。
- 媒体退役检查消息归属并封闭异步删除竞态，拒绝重复消息误删其他消息已认领的文件引用。
- 新密钥先暂存到独立引用，地址与引用再一次 CAS 发布；离页仍完成已开始的保存。同通道冲突明确提示，不同通道变化可重基。
- 网络失败和不完整流按 `TRANSPORT` 分类，保留取消与原始 cause；HTTP 与 SSE 同类供应商错误给出相同语义，并保留请求 ID。
- 工具调用完成前检查身份非空、唯一且不冲突；允许合法的身份晚到和参数交错。
- Plugins 页补齐通道标题，模型以可展开摘要卡显示；保存与上传状态更清晰。
- 旧媒体服务关闭正确映射取消，开发依赖只在测试中校验精确 SemVer，Windows 包验证使用 junction。

三通道独立；模型 ID 手动；未知模态允许尝试；仅用户强制关闭会阻断。原文件不压缩、不转码、不抽帧；未知配置与请求字段保留；不添加供应商内部重试或统一思考开关。

保存新密钥会让该通道使用独立的托管凭据引用。成功轮换后，旧引用可能仍被其他通道或已准备的请求使用，因此本版保留它；明确未发布的失败会尽力清理本次暂存引用。提交结果未知时保留引用并提示核对，不删除可能已生效的密钥。

## 发布门禁与证据

发布流程先在 Linux / Windows 运行类型检查、回归和 tarball 验证，再以被保留的同一个包运行最多 7 次真实 Coding Plan 请求。每次只发一次请求；音频既可以正常完成，也可以收到清晰的上游拒绝，这两种结果分别记录。

门禁检查两个文本请求、图片和视频完成，以及全部 5 个媒体请求的原字节 SHA-256；语义识别另列，不把模型识别误差当成插件传输错误。发布附件包含 `package-verification.json`、`live-review-results.json`、源码归档和 `SHA256SUMS`。

包验证使用官方文件设置，在两个独立 Node 进程中通过真实 Loader 启动、保存/读回模型、发起 Fake Ark 文本请求并卸载。它证明包与 Host 服务闭环；完整桌面浏览器、系统文件选择器及日常启动命令另按 [本机接手指南](../local-handoff.md) 验收。

同一 tarball 还通过固定 Harness `0.1.1-rc.2` CLI 安装到全新隔离 profile，核对 bundle 恰好一份且两次独立配置 dump 相同；记录见 `cli-install-verification.txt`。

## 已知边界

- 当前账号、通道、模型别名可能拒绝音频；拒绝不会改写模态设置。
- 历史专用媒体块仍可能显示为 JSON；导出会话尚不保证跨电脑携带完整媒体。
- 内容寻址媒体保留供历史消息使用，尚无安全的无引用对象自动回收。
- 本版没有新的完整桌面浏览器视觉验收记录，不把组件测试或进程冷启动等同于实机界面通过。
